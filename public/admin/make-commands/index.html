Workflow reference

Make Commands

Choose what you want to do, then work through its numbered panels. Copy each panel with the button in its upper-right corner.

Before you start

Run these commands in your local afpd-tracker repository. Start with a clean working tree and save browser edits first. Pause when a step says to edit or review files. The && between commands stops a copied panel if a command fails; stop the workflow and resolve that failure before continuing.

Working database commands always use staging and accept no database parameter. calls-from-db saves transcripts; evidence-from-db saves evidence reviews. A Git push, a database upload, and a website deployment each do a different job.

Save admin transcript edits and evidence reviews

Download your saved staging edits, keep a Git copy, and publish the updated staging site.

  1. Get the latest staging branch

    Start with a clean working tree. If git status shows your own unfinished changes, commit them before switching or pulling. Stop if any command fails.

    Get the latest staging branch
    git status --short &&
git switch staging &&
git pull --ff-only origin staging

  2. Download both kinds of admin edits and build

    Save changes in the browser first. calls-from-db downloads transcripts and verified flags; evidence-from-db downloads all evidence groups, notes, confirmations and deletion history. The build refreshes generated pages and transcript text files.

    Download both kinds of admin edits and build
    make calls-from-db &&
make evidence-from-db &&
make build

  3. Review the files, then commit and push

    Review the status and diff summary before copying the next panel. If there are no changes, skip the commit and push.

    Review the files, then commit and push
    git status --short &&
git diff --stat

  4. Commit the reviewed data and generated files

    Commit the reviewed data and generated files
    git add -- data public &&
git commit -m "Save staging radio edits and evidence reviews" &&
git push origin staging

  5. Publish the staging site

    This builds and uploads the staging preview. Exporting evidence does not change public officer association labels.

    Publish the staging site
    make manual-deploy

Upload changed source JSON to the staging database

Use after changing roster data, archive settings or other JSON-managed data. Download admin edits before editing the files.

  1. Get the latest staging branch

    Start with a clean working tree; preserve unfinished local changes first.

    Get the latest staging branch
    git status --short &&
git switch staging &&
git pull --ff-only origin staging

  2. Preserve the current admin edits

    Do this before editing the source JSON. calls-from-db replaces local transcript values with the database values. If you already edited transcripts locally, reconcile those edits before downloading.

    Preserve the current admin edits
    make calls-from-db &&
make evidence-from-db

  3. Edit the JSON, then upload and build

    Pause here to make your intended JSON changes. db-upload currently recreates the JSON-managed database tables, including transcripts. It preserves the separate evidence tables and does not import the evidence snapshot.

    Edit the JSON, then upload and build
    make db-upload &&
make build

  4. Review the changes

    Check the edited source files and generated output before continuing. If there are no Git changes, skip the commit and push.

    Review the changes
    git status --short &&
git diff --stat

  5. Commit and push the reviewed files

    Commit and push the reviewed files
    git add -- data public &&
git commit -m "Update staging source data" &&
git push origin staging

  6. Publish staging

    Publish staging
    make manual-deploy

Save only the evidence review data

Download reviewed and unreviewed groups without exporting transcripts, uploading the database or deploying the site.

  1. Get the latest staging branch

    Start with a clean working tree and save your browser edits first.

    Get the latest staging branch
    git status --short &&
git switch staging &&
git pull --ff-only origin staging

  2. Download every evidence group

    Writes data/db-evidenence-associations.json, including empty groups, notes, speaker confirmations, original sources and deletion records. Identical data produces identical JSON.

    Download every evidence group
    make evidence-from-db

  3. Review the exported file

    This snapshot includes correction notes and will be public when pushed to this repository. If there are no changes, skip the next panel.

    Review the exported file
    git status --short &&
git diff --stat -- data/db-evidenence-associations.json

  4. Commit and push the snapshot

    Commit and push the snapshot
    git add -- data/db-evidenence-associations.json &&
git commit -m "Save staging evidence review snapshot" &&
git push origin staging

Edit or restore the evidence snapshot to staging

An explicit evidence upload. Represented groups receive the file’s notes, clip selections and confirmation flags.

  1. Get the latest staging branch

    Start with a clean working tree. Keep any intended restore file separately so the next download does not replace your only copy.

    Get the latest staging branch
    git status --short &&
git switch staging &&
git pull --ff-only origin staging

  2. Download the current evidence before editing

    Then edit data/db-evidenence-associations.json, or replace it with the snapshot you intentionally want to restore. Keep stable IDs intact. Do not download again until you have uploaded those intended edits.

    Download the current evidence before editing
    make evidence-from-db

  3. Upload the intended file, then download the saved result

    evidence-to-db backs up staging evidence under db/local/ and rehearses the upload first. Existing group revisions advance. Unrepresented groups remain unless a deletion record explicitly removes them. Recordings and transcripts are preserved.

    Upload the intended file, then download the saved result
    make evidence-to-db &&
make evidence-from-db

  4. Review the saved result

    If there are no Git changes, skip the next panel. The admin page reads the database directly, so this action needs no website deployment.

    Review the saved result
    git status --short &&
git diff --stat -- data/db-evidenence-associations.json

  5. Commit and push the saved snapshot

    Commit and push the saved snapshot
    git add -- data/db-evidenence-associations.json &&
git commit -m "Update staging evidence review snapshot" &&
git push origin staging

Publish already committed changes to staging

Use when the desired source changes are already committed. This uploads the site, not the database.

  1. Check the branch and send your commits

    Start with a clean working tree. If the pull reports divergent branches, resolve that before continuing; do not force-push.

    Check the branch and send your commits
    git status --short &&
git switch staging &&
git pull --ff-only origin staging &&
git push origin staging

  2. Build and upload the staging preview

    manual-deploy pulls staging, builds it, and uploads a Worker preview using the staging configuration. It does not run db-upload, evidence-to-db or promote-db.

    Build and upload the staging preview
    make manual-deploy

Recreate the JSON-managed staging tables

A repair workflow for staging. Downloads admin edits first; the separate evidence tables are retained.

  1. Get the latest staging branch

    Start with a clean working tree.

    Get the latest staging branch
    git status --short &&
git switch staging &&
git pull --ff-only origin staging

  2. Preserve edits, reset and rebuild

    db-reset creates a staging backup and recreates JSON-managed rows from the local source files. It retains evidence reviews. The current db-upload policy also recreates all JSON-managed tables.

    Preserve edits, reset and rebuild
    make calls-from-db &&
make evidence-from-db &&
make db-reset &&
make build

  3. Review the preserved files

    If there are no Git changes, skip the commit and push.

    Review the preserved files
    git status --short &&
git diff --stat

  4. Commit and push the reviewed files

    Commit and push the reviewed files
    git add -- data public &&
git commit -m "Preserve staging data before database reset" &&
git push origin staging

  5. Publish staging

    Publish staging
    make manual-deploy

Install dependencies or reconnect Wrangler

Run in the repository directory on your own computer. Authentication opens a browser.

  1. Install the locked dependencies

    Use after cloning the repository or when the dependency lockfile changes.

    Install the locked dependencies
    npm ci

  2. Sign in to Cloudflare

    Use when a database or deployment command reports expired or missing authentication.

    Sign in to Cloudflare
    make wrangler-login

  3. List the current Make commands

    List the current Make commands
    make help

Collect an OpenMHz day

Collector setup for the Pi. This collects metadata; it does not itself download audio, transcribe, upload the database or deploy the site.

  1. Open the collector browser on the Pi desktop

    Leave the browser open. Use 5922 instead of 6001 for Law 2 Northeast.

    Open the collector browser on the Pi desktop
    make openmhz-browser TALKGROUP=6001

  2. Collect the selected day in another terminal

    Replace YYYY-MM-DD with the archive date and choose 6001 or 5922. Run from the repository directory. The collection pipeline has additional audio/transcription workflow steps; do not assume this command publishes a day.

    Collect the selected day in another terminal
    make collect-openmhz DATE=YYYY-MM-DD TALKGROUP=6001

ProductionPromote the staging database to production

Production database action. Copies the entire staging database, including evidence reviews, to production. It does not back up production or deploy the website.

  1. Get the latest staging code

    Start with a clean working tree and finish saving admin edits in the browser. The promotion copies a snapshot of the live staging database; it does not upload the local JSON first.

    Get the latest staging code
    git status --short &&
git switch staging &&
git pull --ff-only origin staging

  2. Replace the production database with staging

    This is the only database Make command that writes to production. It retains a staging snapshot under db/local/ and does not back up the previous production database. No source or target database argument is accepted.

    Replace the production database with staging
    make promote-db

ProductionPublish the staging website to production

Production website action. Promotes the staging branch to main and deploys the site. It does not promote the database.

  1. Check and push the intended staging commit

    Use a clean working tree with all intended changes committed. Review the staging site first. Resolve pull or push failures before continuing.

    Check and push the intended staging commit
    git status --short &&
git switch staging &&
git pull --ff-only origin staging &&
git push origin staging

  2. Promote the branch and deploy production

    prod-manual-deploy runs promote-staging, which replaces main with staging using force-with-lease, then builds and deploys production. Use promote-staging alone only when you want the branch promotion without deployment. Run the separate production database workflow only if that copy is also intended.

    Promote the branch and deploy production
    make prod-manual-deploy
